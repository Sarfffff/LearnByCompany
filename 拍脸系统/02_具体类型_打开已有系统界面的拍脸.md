# 具体类型：打开已有系统界面的拍脸（新手奖励本地实例）

> 本文只讲：**复用已有 SceneId，通过一个拍脸 Item 直接打开已存在的 Window。**  
> 当前实例目标 Window：`_MOE.WindowName.UI_NoviceReward_MainView`。  
> 当前配置和 Lua 均为本地链路实例，**不是新需求可直接复制的正式 ID/排序/业务条件**。

---

## 0. 先判断是否属于“打开已有系统界面”的新增

### 0.1 类型对比

| 情况 | 识别条件 | 是否使用本文 | 应转向 |
|---|---|---:|---|
| 直接打开已有 Window | WindowName 已存在；当前场景允许打开；不需要 ActivityModel 根据活动配置选页 | **是** | 按本文 Step 1～6 |
| 按活动 ID 打开活动详情 | 已有真实 `activityId`，且 `ActivityModel:ShowPushFaceActivity` 已有活动映射 | 否 | 通用模板“通过 ActivityModel 打开活动页”分支 |
| 目标 UI 尚不存在 | Window、资源或打开入口尚未实现 | 否 | 先完成 UI/业务功能，再接拍脸；不要在 Item 中虚构 WindowName |
| 需要异步资源/数据 | UI 打开前必须下载资源、请求协议或等待模型就绪 | 不直接使用 | 通用模板“异步资源/数据准备”分支；先设计就绪和失败推进 |
| 纯逻辑、没有 UI | 只发事件、打点、刷新或执行一次逻辑 | 否 | 通用模板“纯逻辑”分支；`HandleShow` 完成后 `return false` |
| Feature 内已有 UI | 配表 `featureName` 非空，Window/业务模型属于副玩法包 | 仅复用本文接口思路 | Item 放 `Feature/<featureName>/Script/PushFace/Items/`，并验证 Feature 包加载 |

### 0.2 使用本文的必要条件

全部满足才使用本文：

- [ ] 已从源码确认目标 WindowName 存在。
- [ ] 已确认 Window 可在目标 Scene 和窗口层级状态下打开。
- [ ] 已确认需要直接 `OpenWindow`，而不是 ActivityModel、跳转系统或 Feature 专用入口。
- [ ] 已确认打开参数；若无参数，也经过源码/现有调用点确认。
- [ ] 已有可复用 SceneId；若没有，先返回通用模板“新增全新 SceneId”。
- [ ] 已有正式 `NeedShow` 条件；若暂时恒 true，仅限本地测试。

### 0.3 快速判断

```text
目标界面已存在？
├─ 否 → 先实现 UI，不使用本文
└─ 是
   ├─ 应由 activityId 决定活动详情？
   │  ├─ 是 → ActivityModel 分支
   │  └─ 否
   ├─ 是否依赖尚未就绪的数据/资源？
   │  ├─ 是 → 异步准备分支
   │  └─ 否
   ├─ 是否真的会打开一个可关闭的 UI？
   │  ├─ 否 → 纯逻辑分支，HandleShow 返回 false
   │  └─ 是 → 使用本文：NeedShow + OpenWindow
   └─ 是否属于 Feature？
      ├─ 是 → 使用 Feature Item 目录
      └─ 否 → 使用主玩法 Items 目录
```

### 2.3 正式业务框架：直接打开新手奖励 Window

```lua
local function _NeedShowNoviceReward(SceneId, activityId, id)
    local model = <已确认的新手奖励业务Model>
    if not model then
        return false
    end

    -- 只调用源码已存在、语义已确认的正式接口
    return model:<已确认的CanShow接口>(activityId)
end

return {
    NeedShow = function(SceneId, activityId, id)
        return _NeedShowNoviceReward(SceneId, activityId, id)
    end,

    HandleShow = function(SceneId, activityId, id)
        -- 若在消费到此项时条件可能变化，可在这里做最后防御
        if not _NeedShowNoviceReward(SceneId, activityId, id) then
            return false -- 没有打开 UI，立即推进
        end

        _MOE.Models.PushFaceModel:AddPushFaceItemCount()
        _MOE.UIManager:OpenWindow(
            _MOE.WindowName.UI_NoviceReward_MainView
        )
        -- OpenWindow 当前通常没有有意义的成功返回值；成功发起打开后可不返回
        -- 不要为了“统一格式”写死 return true
    end
}
```

模板中的 `<已确认...>` 必须替换为源码真实对象和接口；本文不代填、也不虚构。

### 2.4 `HandleShow` 返回值必须正确

| 场景 | 应如何返回 | 原因 |
|---|---|---|
| 已调用 `OpenWindow`，等待窗口关闭推进 | `nil` / 无返回通常即可 | 当前关闭事件会触发下一拍脸 |
| 打开 API 自身返回有意义结果 | `return result` | 保留真实成功/失败语义 |
| 条件变化、业务 Model 缺失、打开 API 明确失败 | `return false` | 没有 UI 可关闭，框架需立即推进 |
| 纯逻辑完成 | `return false` | 同上 |
| 无论什么都 `return true` | **禁止** | 会掩盖未打开 UI的失败，可能卡住队列 |

当前 `UIManager:OpenWindow` 没有稳定的有意义成功返回值；它还可能因资源依赖或竖屏窗口限制提前返回。因此若业务需要可确认的打开结果，应使用业务已有、返回语义明确的封装，而不是擅自把 `OpenWindow` 包装成恒 `true`。

| 用例 | 操作 | 预期 |
|---|---|---|

| 迁移目标 | 配表 `codeName` | `NeedShow` | `HandleShow` | 额外确认 |
|---|---|---|---|---|
| 商城已有界面 | `<ShopPushFaceCodeName>` | `<ShopModel>:<CanShowMethod>(...)` | `<ShopOpenAPI>(<已确认参数>)` 或 `OpenWindow(<ShopWindowName>)` | 页签参数、商品数据是否就绪、场景是否允许 |
| 签到已有界面 | `<CheckInPushFaceCodeName>` | `<CheckInModel>:<HasRewardOrCanShow>(...)` | `<CheckInOpenAPI>(...)` | 是直接 Window 还是 ActivityModel；活动 ID是否真实存在 |
| 其他主玩法界面 | `<BusinessPushFaceCodeName>` | `<BusinessModel>:<CanShow>(...)` | `OpenWindow(<BusinessWindowName>, <Args>)` | WindowName、参数、资源依赖、关闭事件 |
| Feature 内已有界面 | `<FeaturePushFaceCodeName>` | `<FeatureModel>:<CanShow>(...)` | `<FeatureModel>:<Open>(...)` | 填真实 `featureName`；Item 放 Feature 目录；包体加载 |
| 打开 API 有返回值 | `<CodeName>` | `<FormalCondition>` | `return <OpenAPI>(...)` | 明确 false 是否代表未打开；不要吞掉结果 |
| 打开 API 无返回值 | `<CodeName>` | `<FormalCondition>` | `OpenWindow(<WindowName>, ... )` 后不返回 | 确认调用确实发起打开，失败前置要返回 false |

替换时不能只换 WindowName；至少重审：

```text
SceneId
→ featureName
→ NeedShow 条件
→ 打开参数
→ 异步依赖
→ frequency
→ 同 Scene sortId
→ 关闭推进
```

## 5. 常见错误与排查

## 5.1 常见错误

| 错误 | 现象 | 正确处理 |
|---|---|---|
| 复用 `1000128` | 配置覆盖/冲突 | 它已被本地实例占用；新需求重新查重 |
| 直接改 `PushFaceData_Total.txt` | 重导后丢失、环境不一致 | 改 `P_拍脸.xlsx` 后 Compile → Pbin |
| `sortId` 越大越先的误判 | 展示顺序相反 | 当前是降序排、队尾消费，较小值先 |
| 正式保留 `NeedShow=true` | 每次满足框架条件都入队 | 替换正式活动/奖励/数据条件 |
| `HandleShow` 恒 `return true` | 未开 UI 时队列等待关闭事件 | 失败返回 false；成功传播真实结果或不返回 |
| 未打开 UI却无返回 | 当前队列卡住 | 返回 false，立即推进 |
| WindowName 拼错 | 加载/打开失败 | 从 `_MOE.WindowName` 和现有调用点查证 |
| 忽略资源依赖 | `OpenWindow` 被资源检查拦截 | 采用业务正式打开入口或设计资源就绪链路 |
| `AddPushFaceItemCount` 先于明确失败 | 统计虚高 | 有业务返回结果时，仅在 `result ~= false` 后计数 |
| 把七日 BP 参考当正式需求 | 条件、活动、界面错误 | 由产品/业务确认是否真正采用三个参考接口 |
| Feature 配表却放主目录 | require 失败 | `featureName` 与 Item 路径一致 |
